### 1.2. Mapeo a tablas y columnas de Supabase

El colector orquestado en `services/collector/main.py` ejecuta `build_daily_payload()` y persiste el resultado en la base de datos PostgreSQL de Supabase mediante `services/collector/supabase_client.py`:

```
Garmin Connect API
        │
        ▼
garmin_coaching/collector.py (Payload unificado)
        │
        ▼
services/collector/supabase_client.py
        ├─────────► public.readiness_daily
        ├─────────► public.training_load
        ├─────────► public.daily_snapshots
        ├─────────► public.session_log
        ├─────────► public.weekly_sport_load
        └─────────► public.garmin_tokens (tokens SSO obsoletos)
```

#### A. Tabla `public.readiness_daily`
- `user_id`: Identificador del usuario (`00000000-0000-0000-0000-000000000001` en MVP, enlazado vía `coach_profile_links`).
- `readiness_date`: Fecha calendario (`YYYY-MM-DD`).
- `zone`: Clasificación calculada en `garmin_coaching/readiness.py` (`VERDE`, `AMARILLO`, `ROJO`).
- `score_ok`: Conteo de métricas en rango objetivo (0 a 5).
- `sleep_h`: Horas de sueño (`dailySleepDTO.sleepTimeSeconds / 3600.0`).
- `sleep_score`: Puntuación de sueño (`dailySleepDTO.sleepScores.overall.value`).
- `hrv`: HRV promedio nocturno (`avgOvernightHrv`).
- `stress`: Nivel de estrés medio del día (`avgStressLevel`).
- `bb_change`: Recarga neta de Body Battery nocturna (`bodyBatteryChange`).
- `hrv_status`: Estado cualitativo (`BALANCED`, `UNBALANCED`, etc.).
- `thresholds`: Umbrales dinámicos derivados de la mediana de 60 días (`th`).
- `recommendation`: Mensaje prescriptivo generado según la zona fisiológica.
- `payload`: JSONB completo con todas las métricas intermedias.
- `updated_at`: Marca de tiempo generada por trigger.

#### B. Tabla `public.training_load`
- `user_id`: UUID del usuario.
- `load_date`: Fecha de la métrica (`YYYY-MM-DD`).
- `status_phrase`: Estado del entrenamiento (`PRODUCTIVE`, `MAINTAINING`, `OVERREACHING`, etc.).
- `acwr`: Acute:Chronic Workload Ratio (`dailyAcuteChronicWorkloadRatio`).
- `vo2max`: VO2 Máx genérico (`vo2MaxPreciseValue` o `vo2MaxValue`).
- `lthr`: Umbral de lactato en formato JSONB.
- `payload`: JSONB con el volcado completo de `mostRecentTrainingStatus` y `mostRecentVO2Max`.
- `updated_at`: Marca de tiempo.

#### C. Tabla `public.weekly_sport_load`
- `user_id`: UUID del usuario.
- `week_start`: Lunes de inicio de la semana (`YYYY-MM-DD`).
- `block_index`: Número de bloque en el mesociclo planificado.
- `week_in_block`: Semana del bloque (1 a 4).
- `kind`: Tipo de semana (`LOAD`, `RECOVERY`).
- `phase_code`: Código de la fase del macrociclo (`BASE_1`, `BUILD`, etc.).
- `planned_run_min`, `planned_bike_min`, `planned_swim_min`, `planned_walk_min`, `planned_total_min`: Minutos planificados por disciplina en `garmin_coaching/mesocycle.py`.
- `executed_run_min`, `executed_bike_min`, `executed_swim_min`, `executed_walk_min`, `executed_other_min`, `executed_total_min`: Minutos reales ejecutados, agregados desde `get_activities_by_date` mediante `activity_duration_min` y clasificados por `classify_sport()`.
- `payload`: JSONB detallando el plan vs. lo ejecutado.

#### D. Tabla `public.daily_snapshots`
- `user_id`: UUID del usuario.
- `snapshot_date`: Fecha del snapshot.
- `payload`: Estructura raíz que consolida `readiness`, `training_load`, `last_activity`, `mesocycle_week`, `weekly_sport_load`, `session`, `macrocycle`, `milestones` y el mensaje de WhatsApp.
- `health_score`: Puntuación consolidada opcional.

#### E. Tabla `public.garmin_tokens` (Mecanismo transitorio actual)
- `user_id`: UUID del usuario.
- `token_data`: JSONB con `di_token`, `di_refresh_token` y credenciales de sesión generadas por `garth` / `garminconnect.client`. **Esta tabla quedará obsoleta al adoptar la API oficial**.

## 2. Matriz de compatibilidad y paridad con la API Oficial de Garmin

### 2.1. Tipos de credenciales y programas en el ecosistema Garmin

Garmin no cuenta con una única "API Key", sino con tres modelos arquitectónicos radicalmente distintos:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                                MODELOS DE INTEGRACIÓN GARMIN                           │
├─────────────────────────┬──────────────────────────────────┬───────────────────────────┤
│    Personal API Tier    │     Business Developer Program   │   python-garminconnect    │
│  (Personal API Key)     │  (Health / Activity / Training)  │    (Ingeniería inversa)   │
├─────────────────────────┼──────────────────────────────────┼───────────────────────────┤
│ • Uso personal/atleta   │ • Aplicaciones multiusuario      │ • Emulación de app web/iOS│
│ • Gratuito, autogestion │ • Requiere aprobación corporativa│ • Sin contrato ni soporte │
│ • Token OAuth2 Bearer   │ • OAuth 2.0 PKCE / OAuth 1.0a    │ • Tokens SSO di_token     │
│ • REST Pull-only        │ • Push Webhooks obligatorios     │ • REST Pull (web privada) │
│ • personal.connectapi   │ • healthapi / apis.garmin.com    │ • connect.garmin.com      │
└─────────────────────────┴──────────────────────────────────┴───────────────────────────┘
```

1. **Garmin Connect Personal API** (`https://personal.connectapi.garmin.com`):
   - **Propósito**: Lanzado oficialmente por Garmin para desarrolladores individuales, atletas y proyectos de investigación que solo necesitan consultar los datos de su **propia** cuenta.
   - **Autenticación**:
     - Se genera una **Personal API Key** estática directamente en el portal web de Garmin Connect (*Configuración de la cuenta > Información de la cuenta > Personal API Key*).
     - La aplicación intercambia dicha clave por un token de acceso OAuth 2.0 Bearer:
       ```http
       POST https://personal.connectapi.garmin.com/personalapitoken-service/personal-api/personal-api-key/token
       Authorization: ApiKey <TU_PERSONAL_API_KEY>
       ```
     - La respuesta devuelve un `access_token` Bearer con vigencia de hasta 24 horas.
   - **Mecanismo de transporte**: **REST Pull puro**. Ideal para servicios como el collector de Tri-Coach, que se ejecuta mediante cron diario sin requerir una URL pública abierta a la web.

2. **Garmin Connect Developer Program — Business Starter / Enterprise**:
   - **Propósito**: Aplicaciones comerciales para múltiples usuarios (Health API, Activity API, Training API, Courses API).
   - **Autenticación**: Flujo OAuth 2.0 con PKCE o OAuth 1.0a para que cada atleta autorice a la aplicación de Tri-Coach en una pantalla de consentimiento de Garmin.
   - **Mecanismo de transporte**: **Push Webhooks (o Ping/Pull)**. Garmin exige registrar un webhook HTTPS público. Cada vez que el reloj sincroniza con los servidores de Garmin, su backend emite una petición `POST` con un lote de JSONs hacia el servidor del desarrollador.
   - **Límites**: El nivel Starter es gratuito hasta 1,000 usuarios activos, pero **no incluye backfill histórico** (solo recibe datos a partir del momento de la vinculación).

3. **Librería no oficial `python-garminconnect` (Estado actual)**:
   - **Autenticación**: Emulación de credenciales de navegador y cliente móvil iOS mediante `curl_cffi` para falsificar huellas TLS, evadir el WAF de Cloudflare y obtener tokens de sesión `di_token`.
   - **Fragilidad**: Elevada tasa de degradación por bloqueos periódicos de IP, retos de Cloudflare, expiración silenciosa de cookies y necesidad de almacenar secretos en base64 (`GARMINTOKENS_B64`).

## 3. Viabilidad de abandonar `python-garminconnect` y extraer Tri-Coach

### 3.1. Evaluación técnica y cumplimiento de Clean Architecture (`ADR-002`)

La arquitectura actual de Tri-Coach fue diseñada de forma preventiva bajo **Clean Architecture** (`memory/long/adr/ADR-002-clean-architecture-regla-de-dependencia.md`):
- `garmin_coaching/` **no depende** de `garminconnect`, `garth`, `requests` ni `curl_cffi`. Es un paquete puramente algorítmico y de modelado fisiológico que implementa reglas de dominio e inyección de dependencias mediante duck-typing (`client: Any`).
- Todo el acoplamiento con la librería externa radica en:
  1. `services/collector/main.py`: invoca `login_client(prompt=False)`.
  2. `scripts/garmin_auth.py`: gestiona el flujo de login interactivo, Keychain y Supabase.
  3. `pyproject.toml`: declara las dependencias pesadas (`curl_cffi`, `ua-generator`, etc.).

#### Diseño del nuevo adaptador oficial en `services/collector/`

Para sustituir `python-garminconnect` por un cliente oficial sin alterar el dominio, basta con implementar en la capa de infraestructura (`services/collector/garmin_official_client.py`) una clase ligera que cumpla el contrato esperado por `garmin_coaching/collector.py`:

```python
"""Cliente HTTP oficial para Garmin Connect Personal API."""
import os
import requests
from datetime import datetime, timedelta, timezone

class GarminOfficialClient:
    BASE_URL = "https://personal.connectapi.garmin.com"
    TOKEN_URL = f"{BASE_URL}/personalapitoken-service/personal-api/personal-api-key/token"

    def __init__(self, api_key: str | None = None):
        self.api_key = api_key or os.environ.get("GARMIN_PERSONAL_API_KEY")
        if not self.api_key:
            raise ValueError("GARMIN_PERSONAL_API_KEY environment variable required")
        self._token: str | None = None
        self._token_expires_at: datetime | None = None

    def _ensure_token(self) -> str:
        now = datetime.now(timezone.utc)
        if self._token and self._token_expires_at and now < self._token_expires_at:
            return self._token

        # Intercambio de API Key por Bearer token (OAuth 2.0)
        res = requests.post(
            self.TOKEN_URL,
            headers={"Authorization": f"ApiKey {self.api_key}"},
            timeout=10,
        )
        res.raise_for_status()
        data = res.json()
        self._token = data["access_token"]
        # Margen de seguridad: expira en 24h
        expires_in = data.get("expires_in", 86400)
        self._token_expires_at = now + timedelta(seconds=expires_in - 300)
        return self._token

    def _get(self, path: str, params: dict | None = None) -> dict:
        token = self._ensure_token()
        url = f"{self.BASE_URL}{path}"
        res = requests.get(
            url,
            headers={"Authorization": f"Bearer {token}", "Accept": "application/json"},
            params=params,
            timeout=15,
        )
        res.raise_for_status()
        return res.json()

    # Métodos equivalentes para garmin_coaching:
    def get_sleep_data(self, cdate: str) -> dict:
        return self._get("/sleep-service/sleep/dailySleep", params={"date": cdate})

    def get_stress_data(self, cdate: str) -> dict:
        return self._get("/usersummary-service/usersummary/daily", params={"calendarDate": cdate})

    def get_hrv_data(self, cdate: str) -> dict:
        return self._get(f"/hrv-service/hrv/{cdate}")

    def get_body_battery(self, cdate: str) -> dict:
        # En Personal API se obtiene desde usersummary
        return self._get("/usersummary-service/usersummary/daily", params={"calendarDate": cdate})

    def get_activities_by_date(self, start: str, end: str) -> list[dict]:
        return self._get(
            "/activitylist-service/activities/search/activities",
            params={"startDate": start, "endDate": end, "limit": 1000},
        )

    def get_last_activity(self) -> dict | None:
        activities = self._get(
            "/activitylist-service/activities/search/activities",
            params={"start": 0, "limit": 1},
        )
        return activities[0] if isinstance(activities, list) and activities else None
```

#### Solución para Training Status y ACWR en el dominio puro

Al no disponer del endpoint no público `metrics-service`, el dominio de Tri-Coach asume la responsabilidad del cálculo de carga aguda y crónica:
1. `activity_load.py` ya consulta 120 días de actividades vía `get_activities_by_date`.
2. Cada actividad en Garmin reporta su carga individual en `activityTrainingLoad` (o en su defecto se calcula vía TRIMP con duración y FC media).
3. **Fórmula estándar de Gabbett**:
   $$\text{Carga Aguda (7d)} = \sum_{t=0}^{6} \text{Load}_t$$
   $$\text{Carga Crónica (28d)} = \frac{1}{4} \sum_{t=0}^{27} \text{Load}_t$$
   $$\text{ACWR} = \frac{\text{Carga Aguda}}{\text{Carga Crónica}}$$
4. **Mapeo de `status_phrase`**:
   - Si $\text{ACWR} > 1.5 \rightarrow \texttt{OVERREACHING}$ (activa el guard de sobreesfuerzo en `guards.py`).
   - Si $1.3 < \text{ACWR} \le 1.5 \rightarrow \texttt{HIGH\_LOAD}$.
   - Si $0.8 \le \text{ACWR} \le 1.3 \rightarrow \texttt{PRODUCTIVE}$.
   - Si $\text{ACWR} < 0.8 \rightarrow \texttt{RECOVERY}$.

**Ventaja cualitativa**: Tri-Coach deja de depender de las variaciones o anomalías del algoritmo cerrado de Garmin, ganando total explicabilidad para el atleta y el modelo de IA.

## 4. Recomendación accionable para HITL

### 4.1. Veredicto formal: **HÍBRIDO CONDICIONAL HACIA GO (EN 2 FASES)**

- **Dictamen**: **GO** rotundo para la ingesta diaria, lectura de salud, sueño, HRV, estrés y actividades mediante la **Personal API Key** de Garmin.
- **Justificación**:
  1. **Fin de la fragilidad operativa**: El mayor punto de falla en producción ha sido la autenticación SSO de `python-garminconnect` (bloqueos por Cloudflare en Railway, expiración de tokens, prompts MFA, rotación de `GARMINTOKENS_B64`). La Personal API Key resuelve esto al 100% mediante una credencial oficial diseñada para no expirar y sin retos antibot.
  2. **Cero costo de infraestructura adicional**: Al operar en modo **Pull**, no se requiere transformar la arquitectura del collector en un servidor de webhooks persistente con encolamiento asíncrono.
  3. **Independencia en analítica de carga**: Calcular ACWR internamente no es una pérdida, sino una mejora sustancial que desacopla a Tri-Coach de la lógica opaca de Garmin y cumple con la literatura deportiva de Gabbett.
  4. **Excepción controlada (Fase Híbrida)**: Si Diego utiliza frecuentemente la subida automática de planes al reloj (`publish_weekend_readiness_plan.py`), se mantiene ese script en local bajo demanda con la librería no oficial o se programa manualmente en Garmin Connect, mientras que el 100% de la aplicación web y del worker diario opera sobre la API oficial.
